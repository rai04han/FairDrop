### 7.2 Top 5 Risks to the Demo

1. **Dual-Database Disconnect (MongoDB vs MySQL):**
   *Risk:* Rider signup in core-service (MongoDB) does not automatically create or sync the corresponding record in pay-service (MySQL), causing `POST /api/pay/calculate` to fail with "Rider not found" during the live demo.  
   *Mitigation:* T2 unified seed script guarantees identical IDs on clean setup; T4 ensures `/api/pay/calculate` upserts missing riders; T5 adds automatic sync with rollback at registration.

2. **Android Release Build Network Failure (Cleartext / Manifest):**
   *Risk:* The app builds successfully in debug mode on the emulator, but when installed as a release APK on the physical phone for customer/restaurant/admin testing, all HTTP requests fail silently because `INTERNET` permission and `usesCleartextTraffic="true"` are missing from `main/AndroidManifest.xml`.  
   *Mitigation:* T1 fixes the manifest immediately before any UI work; T20 verifies the release APK on a physical device.

3. **Missing Restaurant & Customer Shells (Role Routing Failure):**
   *Risk:* Steps 2, 3, 4, 7, 12, and 13 depend on logging into the mobile app as restaurant, customer, or admin on the physical phone. Currently, customer and restaurant logins are hard-routed to `/unsupported-role`.  
   *Mitigation:* T10, T14, and T15 replace the unsupported-role screen with dedicated shells and views.

4. **Missing Idempotency and Timing Drift in Live Delivery Flow:**
   *Risk:* If a rider taps "Delivered" twice or network retries occur, pay-service currently returns a `409 Duplicate Order` error, breaking the delivery summary screen. Additionally, if wait compensation is tested before the 1-minute threshold elapses, wait compensation will show ₹0.00 instead of a positive number.  
   *Mitigation:* T4 makes `/api/pay/calculate` strictly idempotent; T2 seeds the wait threshold to 1 minute; T8 rounds server wait up to whole minutes.

5. **Lack of Automated Verification (`e2e-smoke.js` missing):**
   *Risk:* Debugging multi-step interactions (customer places → backend allocates → rider accepts → steps → pay calculates) manually on two devices during demo rehearsals is slow and error-prone.  
   *Mitigation:* T18 builds `scripts/e2e-smoke.js` early to test all 13 HTTP steps in seconds and prevent regressions.
